Purple Team/Proof of Concept/SIEM Integrity

Rogue-Agent Log Injection

An anonymous host on the network enrolled itself into the Wazuh SIEM with no credential, became a trusted agent, and injected a forged security alert — a fake SSH brute-force from an attacker-chosen IP — straight into the SOC's trusted alert stream.

Target wazuh-m · 198.51.100.10 Source caldera-c2 · 198.51.100.20 Date 2026-08-20 Scope Wazuh 4.14.5 · authd use_password: no · TCP/1515 reachable Authorized lab · own infrastructure

Overview

The lab is a full home SOC — an OPNsense perimeter, Suricata IDS, and a Wazuh/OpenSearch SIEM watching two Linux hosts. The SIEM is the component meant to see every other attack. This authorized purple-team exercise asks the harder question: what happens when the attacker turns on the SIEM itself?

60-second case summary

The finding in four moves

Entry

TCP/1515 was reachable and use_password: no. The manager issued a valid agent key on demand to an anonymous host; no credential was stolen.

Impact

The rogue endpoint became a trusted agent and inserted an attacker-authored SSH event that Wazuh indexed as rule 5710 beside 34 genuine brute-force alerts.

Response

Missing manager-log inputs were added, enrollment and API-abuse detections were built, and password-protected enrollment was enabled. Repeating the original enrollment command was then rejected.

Boundary

This was a configuration-driven trust failure, not a CVE or direct index compromise. It proved attacker-controlled text could enter trusted telemetry; no LLM consumed it, and prompt injection remains a future test.

Bottom line: The attack forged one believable alert, the evidence exposed detectable inconsistencies, the unauthenticated entry path was closed, and separate deletion-visibility gaps remain documented below.

The mechanism

Crossing the trust boundary

The whole exploit turns on one move: an unauthenticated enrollment converts an untrusted attacker host into a trusted agent. Once across that line, everything the attacker forwards is attributed to a manager-issued, trusted identity. Wazuh still decodes the content and matches it against the same rules — what it stops asking is whether the source should be believed.

Analysis

Why it worked, and what it costs

The flaw

Wazuh's enrollment service (authd, port 1515) ran with use_password: no and was reachable from a neighboring host.

Enrollment is meant to be a brief, trusted bootstrap. Left open, it is an anonymous grant of a trusted identity.

This is not a CVE claim. Nothing here exploits a software defect — authd did exactly what it was configured to do. It is a deployment and trust-boundary failure, in the one component whose value depends entirely on that boundary holding.

The impact

Once trusted, the agent controls a telemetry feed. This exercise demonstrated alert forgery. Misdirection, analyst exhaustion and burying real activity under injected noise are plausible follow-on effects, not outcomes measured here.

This subverts integrity, not just a host — it attacks the thing that is supposed to see every other attack.

The tells

The forged record was not indistinguishable. Three fields separated it from the 34 genuine alerts beside it.

Two may be removable by copying a genuine event shape; that was not re-tested. The strongest leads are enrollment provenance and multi-event session correlation.

The evidence

Two populations in one stream

The preserved export holds 35 alerts — every one of them rule 5710, level 5, attributed to the rogue agent. Thirty-four are genuine internet brute-force that the agent dutifully forwarded. One is fabricated. That ratio is the point: the forgery did not land in a quiet lab, it landed inside a noisy, production-looking stream of real attacks, indexed under the same trusted identity.

the honest readThe forgery cleared the important bar — same decoder, same rule, same severity, same manager-issued agent identity — but it was not a perfect twin. The downloadable CSV makes that row-level comparison inspectable. Whether a more careful forgery removes two of the tells remains a testable hypothesis, not a result of this run.

Tell 1 — blank country

Populated on all 34 genuine rows, blank on the forgery.

The forged source is non-routable TEST-NET-3 space, and this deployment returned no country match for it. Those are observed facts; whether substituting a routable address removes the distinction remains the untested part. (City is blank on 22 of 34 genuine rows, so city-level gaps prove nothing.)

Tell 2 — unparsed port

Populated on all 34 genuine rows, blank on the forgery — 4444 survives only inside full_log.

In this export, the decoder populated data.srcport for the genuine Invalid user … records but not the forged Failed password … record. Copying the genuine phrasing is the obvious next test, not a demonstrated bypass.

Strongest here — session shape

Real sshd traffic is correlated: each of the 17 genuine sessions emitted an Invalid user line and a Disconnected … [preauth] line sharing one PID. The forgery is the only single-event PID in the export.

A coherent multi-line forgery may erase that distinction, but that attack was not executed. Provenance — the newly issued agent identity and its enrollment timeline — is the more durable control point.

Act two · anti-forensics

The SIEM saw the join, but not the erase

The cleanup was deliberately run as a track-covering test (T1070), on the theory that an attacker who owned the SIEM would erase both the foothold and the evidence. At the time of the test, neither action raised an alert.

F6a — removal logged, not alerted

manage_agents -r makes wazuh-authd write Agent 'NNN' (name) deleted (requested locally) to ossec.log, which is ingested.

But built-in rule 505 matches the literal string “Agent removed” — not Wazuh's own wording. The event sat in the pipeline unmatched. A rule-language mismatch, not a missing log.

F6b — bulk deletion is invisible

A single _delete_by_query removed 363 records tagged to the rogue agent. OpenSearch security audit was enabled (audit_rest: true, WRITE not disabled), yet the delete produced no security-auditlog-* entry and no Wazuh alert.

Observed gap: confirmed. Root cause: not yet isolated. The exercise notes point to the handling of admin-certificate operations, but a controlled repeat with explicit audit categories and different administrative identities is needed before attributing the absence solely to that mechanism. Unresolved.

scope boundaryRead this honestly: the deletion was performed with manager-level administrative access, not with the rogue agent's credential. It is a separate scenario — “the attacker already owns the SIEM host or its admin plane” — and not a demonstrated continuation of the anonymous-enrollment chain above. An anonymously enrolled agent could not, on this evidence, erase the index.
takeawayThe monitor detected the attacker joining but not the attacker erasing. Detection on the monitoring host is only as trustworthy as the host's own records — which is the argument for append-only, off-box alert storage.

On the identity mappings. T1136 and T1078 are approximate. A Wazuh agent key is a service/endpoint identity issued by the manager — not a local, domain, or cloud user account — so neither technique fits cleanly. T1136 is the closest analog for creating the unauthorized trusted identity; T1078 for subsequently authenticating with the valid issued credential. T1565.001 is the exact mapping for the forged alert record itself.

Response

detect

Built & live. Enrollment and API brute-force were re-tested as separate behaviors: rule 100361 fired on live enrollment, while built-in 411 fed the 100360 threshold rule and a 600-second firewall-drop.

prevent

The real fix — done. use_password: yes + authd.pass set on authd; the identical enrollment command is now rejected. Still open: bind the API to loopback and firewall the SIEM.

harden

Ship alerts off-box to append-only storage so a compromised SIEM cannot rewrite its own history.

Scope · what held

Not everything was open

A finding is only credible next to what didn't fail. Two controls on the same host worked correctly during the exercise, which is what makes the enrollment gap a specific defect rather than a generally unlocked machine.

Positive controls

Remote syslog rejected the attack host. Ports 514/5514 restrict allowed-ips to the OPNsense firewall only; caldera-c2 was refused there.

The indexer was not reachable from the attack host. Recon found port 9200 closed, and the rogue-agent chain used no direct index access.

Detection needed telemetry first

At the time of the exercise, the Wazuh manager was already writing API authentication failures to /var/ossec/logs/api.log and enrollment messages to /var/ossec/logs/ossec.log. But neither path was declared as a <localfile> input in /var/ossec/etc/ossec.conf, so those records never reached Wazuh's decoders and rules.

Adding the two <localfile> entries completed the pipeline: file → collection → decoding → rule → alert. You cannot detect what you do not collect; a correct rule above a missing input sees nothing and silently never fires.

Detection engineering

Four rules, three validation levels

The rule IDs are not interchangeable proof. The exercise produced live attack validation for two behaviors, a configuration-posture rule, and an offline regression test for cleanup visibility.

100360 · live + response

Aggregates five built-in API-authentication failures (rule 411) in 60 seconds from the same source. A live 19-request replay fired the rule and installed the timed network drop.

100361 · live

Detects the enrollment request in ossec.log. It fired during the live re-run of anonymous enrollment.

100362 · posture

Raises severity when authd announces that no password is required. It detects the vulnerable configuration state, not alert forgery itself.

100363 · logtest

Matches Wazuh's actual agent-deletion wording. It passed wazuh-logtest; a live removal alert remains a future positive-control test.

pipeline firstapi.log and ossec.log were not initially ingested. Adding both as localfile sources made the authentication failures, enrollment and removal records available to rules. The API brute-force was a parallel finding discovered during recon; it was not required for rogue-agent enrollment or forged-alert injection.

Remediation · verified

Found → detected → fixed → re-tested

The unauthenticated enrollment path was closed at the source. Port 1515 still listens — it has to, for legitimate agents — but enrollment now requires a shared secret (use_password: yes + authd.pass). The identical command from Step 3 was re-run to confirm the fix holds.

root@caldera-c2before · vulnerable
echo "OSSEC A:'ROGUE'" | openssl s_client -connect …:1515 -quiet
OSSEC K:'003 ROGUE-TEST-2 any [redacted]'   ← key handed over
root@caldera-c2after · fixed
echo "OSSEC A:'ROGUE'" | openssl s_client -connect …:1515 -quiet
ERROR: Invalid password. Unable to add agent   ← blocked
resultThe unauthenticated foothold is closed. The two rules were validated by different means, and the distinction matters: enrollment rule 100361 fired during a live re-run of the attack, while removal rule 100363 was validated offline with wazuh-logtest and has not yet been observed firing on a live removal. Detection proved the risk; configuration removed it.

Future risk · not exercised

The next trust boundary is the model context

This exercise did not attack an LLM, and no model consumed the fabricated event. It did prove the delivery primitive an AI-assisted SOC must defend: an unauthenticated source persisted attacker-chosen natural language inside the trusted alert corpus that a future analyst model or retrieval pipeline could read.

demonstrated pathproved steps → future boundary
external host
  → anonymous enrollment
  → manager-issued agent identity
  → attacker-chosen full_log
  → rule 5710 alert
  → stored SIEM record
  ⇢ future LLM / RAG context   ← not tested here

Why this becomes injection

If a model is asked to summarize, classify or investigate raw full_log, an attacker can place text where the system expects evidence. If the model interprets that data as instruction, this becomes indirect prompt injection.

Proven here: control of the text and its trusted storage path. Not proven here: model execution, successful instruction following, or downstream action.

Impact scales with agency

A read-only copilot could omit an indicator, downgrade a trace, invent a conclusion or distort an incident summary. A tool-enabled agent could additionally recommend or attempt containment, ticketing or remediation actions.

The second tier depends on the tools and permissions granted to the model; it is a threat-model result, not a claim about this Wazuh deployment.

The validation plan

Test later on a disposable clone with a harmless canary instruction, a read-only model and no operational tools. Compare raw evidence, deterministic-rule output and the model's answer; retain the exact prompt, retrieved context and response.

Only after that baseline should the lab evaluate bounded, human-approved actions.

why it matters nowOWASP and NIST describe indirect prompt injection as model manipulation delivered through attacker-controlled external or resource content. Recent 2026 preprints go one step closer to this lab: they report that adversarial text embedded in security logs can alter LLM triage, summaries and classifications. Those studies do not prove this specific pipeline is exploitable; they establish that the proposed follow-on test is evidence-backed, current and directly relevant.
design ruleTreat every log field as untrusted even after the event is authenticated. Preserve provenance, separate instructions from evidence, correlate across independent signals, constrain model tools with least privilege, require human approval for consequential actions, and audit the model's inputs, outputs and tool calls. Formatting and filtering help, but are not a complete boundary by themselves.

Takeaway

The loop closed end to end — the unauthenticated foothold was proven, its alert-forgery impact was preserved in evidence, detection was built and tested at stated confidence levels, and the anonymous path was then closed at the source. The forward-looking lesson is sharper: a telemetry field can be both an authenticated SIEM record and untrusted model input. Configuration, provenance, correlation, bounded AI authority and tamper-evident off-box storage have to preserve that distinction.

Authorized exercise. Every action was performed by the lab owner against their own infrastructure, in an isolated home-lab SIEM, to validate detection and drive remediation. No third-party systems were involved. The single forged record has been purged from the index; the evidence export is retained. This document is a defensive purple-team artifact.
