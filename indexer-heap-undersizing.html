The Query That Exposed a Broken SIEM

Measuring a week of detection data hit a circuit-breaker error — and uncovered a capacity defect that had no visible service outage. The failed queries exposed a limit that could also affect broader hunts and dashboard searches.

Symptom circuit_breaking_exception Root cause 1 GB heap on a 12 GB host Fixed · verified

Overview

This began as routine measurement — querying daily slices of a week of traffic to tune a detection threshold — and became a capacity finding. A running SIEM can still fail the searches an analyst needs. The measurement exposed that limit here.

The trigger

A routine measurement exposed a capacity limit

It surfaced while deriving a port-scan detection threshold from a week of real traffic — a composite aggregation over the firewall-block events, run one 24-hour slice at a time. Identical each day; only the time range changed.

the catchThe recent one-day slice completed; queries covering earlier slices in the seven-day study hit the parent circuit breaker on a heap already heavily used at rest. The failure establishes memory pressure, but the response does not identify which structures consumed the heap.

The symptom

The recent slice worked; earlier slices failed

The first run hid it. The query piped straight into jq with no error handling, so the error object came back as Cannot iterate over null and read like a client-side bug. Surfacing the raw response showed the truth:

opensearchseven-day measurement · failed query
circuit_breaking_exception: [parent] Data too large … 974.2mb,
which is larger than the limit of 972.7mb
  request=0b   fielddata=102.9kb   in_flight=1.1kb
tellThe parent breaker reported total usage near the heap limit despite small child-breaker reservations. request=0b is the request breaker's accounting at that instant, not a measurement of all memory used by the query; fielddata=102.9kb does not support attributing the failure to a large fielddata allocation.

The diagnosis

Heap pressure without a service crash

Heap

1 GB configured on a host with 12 GB total and ~9 GB free and idle.

Shards

540 on a single node. Shard overhead was a plausible contributor to baseline heap pressure, but per-shard memory usage was not measured.

GC

0 old-generation collections in the captured statistics. That snapshot showed no old-generation collection activity; it does not establish behavior under sustained load.

At-rest heap usage was about 850 MB of 1 GB, leaving limited headroom before the parent-breaker limit. The captured figures do not partition that usage between shards and other structures. The circuit breaker rejected the query; the service remained running, but the failed search was already an operational symptom.

The fix

4 GB, verified, one planned restart

/etc/wazuh-indexer/jvm.optionsafter restart
-Xms1g -Xmx1g   →   -Xms4g -Xmx4g
heap: 4096MB max, 27% used at rest
7-day study: all daily query slices complete, no errors
noteChose 4 GB, not 50%-of-RAM: manager, dashboard and filebeat share the host, and OS page cache is what makes searches fast. Don’t starve it.

Why it mattered

A silent blocker, cleared early

Service uptime hid the limit

The indexer stayed running while searches failed. Service availability alone had not exposed the query limit; a dashboard relying on a failed search could show an empty panel or an error.

Other searches were at risk

Multi-day dashboards, telemetry pilots and historical hunts could encounter the same heap limit. Their outcomes depend on the query and workload; these measurements do not prove that every dashboard would fail.

Shard pressure remains

The heap raise cleared the tested query failures; the 540-shard footprint remains a likely contributor to baseline pressure. The longer-term work is to right-size new indices and reduce existing shard count through retention, deletion or consolidation. An ISM policy can automate the lifecycle, but rollover alone creates another index. Tracked, not urgent.

Operational note recorded for the team: on this single-node cluster, yellow with only unassigned replicas is expected — all primaries are allocated, but there is no replica redundancy. Red means at least one primary shard is unassigned. During this restart it cleared in about a minute as shards recovered; elapsed time alone is not proof of recovery. Check recovery progress and confirm the cluster reaches yellow or green; investigate primaries that remain unassigned.

References: OpenSearch circuit-breaker accounting and cluster-health states.

Takeaway

Raising the heap cleared the tested failures; the value was measuring the search limit. A running monitoring platform still needs to answer the historical queries an analyst relies on. The investigation established the observed heap pressure, a verified capacity improvement, and a remaining shard-sizing concern. It also clarified how to check primary-shard recovery after a restart.
