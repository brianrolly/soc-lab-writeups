What a 9.8 Actually Means

A credentialed scan of my own SIEM returned a CVSS 9.8 Critical. The number says drop everything. The work says something more precise — and doing that work is the difference between an analyst and a scanner.

Finding CVSS 9.8 · bundled Node.js Method credentialed Nessus + OpenVAS triaged · not RCE · still real

Overview

Anyone can run a scanner and forward the PDF. The skill a SOC actually pays for starts after the scan: taking a red CRITICAL and determining what it means in this deployment. This is that process, start to finish, on a real 9.8 — the checks, the evidence, the vendor dead-end, and the honest verdict.

The finding

A critical, in the monitoring stack itself

An authenticated scan read the actual installed versions on the SIEM host. Buried in the results: a CVSS 9.8 in the Node.js runtime bundled inside the dashboard — version 18.19.0, seven CVEs, base score 9.8.

The instinct, and why it's wrong

9.8 does not mean “pop a shell”

A 9.8 on an internet-facing service reads as unauthenticated remote code execution. But the score is an aggregate — the scanner stamps the whole Node.js release bundle with the highest base score in the set. Decompose the bundle and not one constituent is a remote RCE against this host. Each needs a precondition this deployment doesn't meet.

The scanner can't know that — establishing it is the analyst's job, the exact job the number tries to shortcut.

The evidence

Three checks, three dormant code paths

Assertion isn't validation. Each claim above is a command against the live host — and all three say the vulnerable code is present but never reached by the running configuration.

Permission model — off

The high-scoring CVEs need Node's experimental permission sandbox enabled. It isn't.

/proc/737/cmdline →
--no-warnings --max-http-header-size…
no --experimental-permission. You can't bypass a boundary that was never turned on.

HTTP/2 — not spoken

The one CVE with a public exploit is an HTTP/2-only DoS. The dashboard doesn't offer HTTP/2.

openssl s_client -alpn h2,http/1.1 →
ALPN protocol: http/1.1. The vulnerable frame handler is never reached.

Front-end proxy — none

The request-smuggling CVE only bites when a proxy parses headers differently than the Node backend.

The dashboard is the terminating server — no proxy in front, no desync to exploit.

patternSame shape three times over: vulnerable component shipped, vulnerable code path not instantiated. Version-vulnerable is not the same as exploitable, and you only learn the difference by inspecting the actual deployment.

The dead end

The vendor's current release ships it unfixed

The obvious remediation is “upgrade.” So I checked what the next release actually contains — downloaded the candidate packages and inspected them without installing. Both the Node runtime and the log4j the same scan flagged are unchanged.

ComponentInstalledNext vendor releaseActually fixed in
Node.js (dashboard)18.19.018.19.0 — unchanged18.19.1
log4j-core (indexer)2.25.32.25.3 — unchanged2.25.4
soThis is a vendor-pinned vulnerability, not a patch backlog. Upgrading to the current release leaves the 9.8 in place. The fix has to be architectural, not apt upgrade.

Reality check

Twenty CVEs. One runnable exploit. It can't reach here.

The full credentialed scan returned 20 CVEs across the bundled runtimes. I searched for public proof-of-concept code for every one. The result is the whole thesis in a single line.

20CVEs found (all bundled runtimes)
1with clone-and-run POC code
0that reach this endpoint as deployed

The single packaged POC targets the HTTP/2 DoS — and the ALPN check already proved the dashboard speaks only HTTP/1.1. The Windows command-injection CVE has loud public exploits, but this is Linux. The permission-model bugs need the flag that's off. The log4j log-injection has no public POC at all. Nothing in the set is both weaponized and reachable.

The second opinion

Two scanners, same host, opposite blind spots

I ran a second credentialed scanner (OpenVAS) against the identical targets with the same SSH credential. It did not corroborate the finding — it never saw it. And it found things the first scanner missed. Their actionable results barely overlap.

Why one saw it and one didn't

Nessus walks the filesystem hunting runtimes bundled inside other packages — it found node and the log4j jar by path. OpenVAS matches dpkg-registered packages against advisories; a runtime vendored inside another package isn't a dpkg entry, so it's invisible to that method.

The lesson

A second scanner isn't redundant belt-and-suspenders — it covers different ground. The most severe issue in the environment was visible to exactly one of the two. Run only the other, and the 9.8 in the SIEM goes unseen.

The verdict

Not RCE. Still a real finding.

Triage that only ever says “false alarm” is as useless as a scanner that only says “critical.” The honest conclusion here is neither.

What it's notA pop-a-shell 9.8. No remote RCE primitive exists in this bundle, and every reachable path is dormant.
What it isAn internet-facing, unpatched, vendor-pinned runtime. The next Node CVE that is a clean RCE lands on this same exposed surface.
Real riskNot “exploited today.” It's “why is a runtime the vendor won't patch answering the whole internet at all.”
Fix

Restrict reach, since you can't patch what's pinned. Source-restrict the dashboard to known-good networks, or bind it to loopback and reach it over a tunnel — the same control already applied to the C2 admin panel in this lab.

Track

Treat the bundled runtime as a standing exposure with a vendor dependency: re-scan on each release, escalate to the vendor, and hold the compensating control until the pin is lifted.

Takeaway

A CVSS score is a starting point, not a verdict. The 9.8 was real, the component was real, and it faced the internet — and it still wasn't the emergency the number implied, because three checks against the running config showed the vulnerable code was never reached. That gap, in both directions, is the whole job: a scanner reports what it has a plugin for; an analyst determines what's true here. The finding that mattered most in this environment was pinned by a vendor, invisible to one of two scanners, and only understandable after the number stopped being the answer and started being the question.
