What a 9.8 Actually Means

A credentialed scan of my own SIEM returned a CVSS 9.8 Critical. The number says drop everything. The work says something more precise — and doing that work is the difference between an analyst and a scanner.

Finding CVSS 9.8 · bundled Node.js Method credentialed Nessus + OpenVAS Scope Wazuh 4.14.5 · 2026-08-31 triaged · not RCE · still real

Overview

Anyone can run a scanner and forward the PDF. The skill a SOC actually pays for starts after the scan: taking a red CRITICAL and determining what it means in this deployment. This is that process, start to finish, on a real 9.8 — the checks, the evidence, the vendor dead-end, and the honest verdict.

Assessment scope. On 2026-08-31, Nessus and OpenVAS ran credentialed checks against the same Wazuh 4.14.5 host using the same authorized SSH access. The follow-up commands shown here were read-only. I did not send a resource-exhaustion or privilege-escalation payload to the live SIEM.

The finding

A critical, in the monitoring stack itself

An authenticated scan read the actual installed versions on the SIEM host. Buried in the results: a CVSS 9.8 in the Node.js runtime bundled inside the dashboard — version 18.19.0, seven CVEs, base score 9.8.

and worseThat exact binary is not sitting idle on disk. It is the process listening on the network — the dashboard people log into.
wazuh-mss -tlnp

LISTEN 0.0.0.0:443  users:(("node",pid=737))
wazuh-mresolve the listener to its executable and version
readlink -f /proc/737/exe
/usr/share/wazuh-dashboard/node/bin/node

identityThe listener resolves to the same path and version the credentialed plugin reported. This closes the gap between a vulnerable file found on disk and the process actually serving TCP 443.
wazuh-mand what privilege does that listener actually hold?
grep -E 'Uid|CapEff' /proc/737/status; capsh --decode=0x400
Uid:     111  111  111  111
CapEff:  0000000000000400
0x0000000000000400 = cap_net_bind_service   — and nothing else
the subtletyIt runs as an unprivileged service account (UID 111) with exactly one capability: cap_net_bind_service, the grant that lets a non-root process bind a port below 1024. That capability is the intended exception to Node's environment-variable filtering rule in CVE-2024-21892. The bug is that Node mistakenly extends that exemption to processes that also hold other capabilities — and this one holds none. So the vulnerable capability combination isn't “met but unreachable”; it is simply absent. The chain settles it end to end: tcp/443 → pid 737 → node 18.19.0 → uid 111 → CapEff 0x400 → only cap_net_bind_service → intended exception.

The instinct, and why it's wrong

9.8 does not mean “pop a shell”

A 9.8 on an internet-facing service reads as unauthenticated remote code execution. But the score is an aggregate, and the bundle spans three release lines — Node 18, 20 and 21. The installed runtime is Node 18 (“Hydrogen”). Decompose the bundle against the actual branch and the host-level 9.8 interpretation evaporates: its top-scoring CVEs are permission-model bugs that don't exist in Node 18 — they belong to the Node 20/21 portions of the plugin. Of the seven, only three touch this branch, and none is a remote RCE.

Version-matching a mixed-branch bundle is not the same as assessing a host.

The evidence

Applicable is not the same as reachable

Assertion isn't validation. Each check below is a command against the live host. Together they take the CVEs that do apply to Node 18 and narrow them to a single plausibly-reachable availability issue.

Permission model — not in this branch

The high-scoring CVEs target Node's permission model, which was added in Node 20 (“Iron”). This runtime is Node 18 (“Hydrogen”) — the feature, and those CVEs, don't exist here.

/proc/737/cmdline shows no --experimental-permission, because Node 18 has no such flag. Not a config gap — a branch mismatch.

HTTP/2 — not spoken

The two HTTP/2 DoS CVEs (including the one with a public POC) need the server to speak HTTP/2. The dashboard doesn't offer it.

openssl s_client -alpn h2,http/1.1 →
ALPN protocol: http/1.1. Those frame handlers are never reached.

Front-end proxy — none

The request-smuggling CVE only bites when a proxy parses headers differently than the Node backend.

The dashboard is the terminating server — no proxy in front, no desync to exploit.

HTTP/1.1 — spoken, and this is the one live edge

CVE-2024-22019 is an HTTP/1.1 chunked-extension DoS, and the dashboard answers HTTP/1.1. This establishes protocol reachability, but not reproduced resource exhaustion.

Availability only — no shell, no data — and plausibly reachable, so it stays on the board. I did not send the destructive payload to the live SIEM; confirming impact belongs on a disposable clone.

patternThe shape holds for nearly all of them: vulnerable component shipped, vulnerable code path not instantiated. The one exception — an HTTP/1.1 DoS — is what proves the method works: validation surfaces the single real edge instead of dismissing the whole set.

The dead end

The vendor's current release ships it unfixed

The obvious remediation is “upgrade.” The host was running Wazuh 4.14.5, so I downloaded the 4.14.7 candidate packages from the vendor repository and inspected them without installing. Package listing identified the bundled log4j jar; extracting the dashboard payload and running its bundled Node binary with --version identified the runtime. Both components the scan flagged are unchanged.

ComponentWazuh 4.14.5Wazuh 4.14.7 packagePlugin clears at
Node.js (dashboard)18.19.018.19.0 — unchanged18.19.1
log4j-core (indexer)2.25.32.25.3 — unchanged2.25.5
soThis is a vendor-pinned vulnerability, not a patch backlog — the current release leaves it in place. And 18.19.1 would only clear the plugin: Node 18 reached end-of-life on 2025-03-27, so the runtime is unsupported regardless. Immediate mitigation is architectural access restriction; permanent remediation needs a vendor-supported runtime.

Reality check

Twenty CVEs. Validation narrows them to one.

Seven CVEs came from the 9.8 finding above. Additional Node.js release-bundle findings and four log4j findings brought the credentialed-scan inventory to 20 CVEs across the two bundled runtimes. Branch applicability, then deployment reachability, then a public-PoC search for each produced the four numbers below.

I found one public clone-and-run PoC in the set as of 2026-08-31: an HTTP/2 DoS (CVE-2024-27983). The ALPN check shows the dashboard speaks no HTTP/2, so that PoC cannot reach this endpoint. The Windows command-injection CVE has public exploit code, but this host is Linux. The permission-model bugs aren't in this release line. I found no public PoC for the log4j log-injection. One HTTP/1.1 availability issue stays plausibly reachable. No remotely reachable RCE primitive was identified in this Linux deployment, and “no public PoC found” is not the same as “safe.”

The second opinion

Two scanners, same host, opposite blind spots

I ran a second credentialed scanner (OpenVAS) against the identical targets with the same SSH credential. It did not corroborate the finding — it never saw it. And it found things the first scanner missed. Their actionable results barely overlap.

Why one saw it and one didn't

Nessus walks the filesystem hunting runtimes bundled inside other packages — it found node and the log4j jar by path. The OpenVAS checks that ran here enumerated the host's OS packages but did not identify the vendored runtimes. Whatever the exact matching logic, the observed result is a blind spot for bundled dependencies — exactly where this finding lived.

The lesson

A second scanner isn't redundant belt-and-suspenders — it covers different ground. The most severe issue in the environment was visible to exactly one of the two. Run only the other, and the 9.8 in the SIEM goes unseen.

One more claim worth proving rather than trusting: that the OS packages OpenVAS listed really were patched, so a severity-0 verdict is correct and not a miss. OpenVAS logged the OpenSSH regreSSHion RCE (CVE-2024-6387) among them — the kind of name that stops a shift.

wazuh-mis regreSSHion actually present, or backport-patched?
dpkg -l openssh-server | awk '/^ii/{print $3}'
1:9.6p1-3ubuntu13.18
# Ubuntu fixed CVE-2024-6387 in 1:9.6p1-3ubuntu13.3
13.18 > 13.3  →  backport-patched, not vulnerable
why this mattersThe upstream version string stays 9.6p1 for the life of the release — Ubuntu backports the fix and records it in the -3ubuntu13.18 suffix, not the headline number. A check that matches on 9.6p1 alone flags a patched host; a distro-aware one reads the suffix and stays quiet. Both scanners got it right here — Nessus omitted it, OpenVAS logged it at severity 0 — and confirming why is the difference between trusting a clean line and knowing it's clean.

The verdict

Not RCE. Still a real finding.

Triage that only ever says “false alarm” is as useless as a scanner that only says “critical.” The honest conclusion here is neither.

What it's notA pop-a-shell 9.8. No remotely reachable RCE primitive was identified in this Linux deployment. Of 20 CVEs, nine don't apply to this branch or OS, ten lack a verified reachable path as deployed, and one HTTP/1.1 DoS stays plausibly reachable — availability only.
What it isAn internet-facing, unpatched, vendor-pinned runtime. The next Node CVE that is a clean RCE lands on this same exposed surface.
Real riskNot “exploited today.” It's “why is a runtime the vendor won't patch answering the whole internet at all.”
Fix

Restrict reach, since you can't patch what's pinned. Source-restrict the dashboard to known-good networks, or bind it to loopback and reach it over a tunnel — the same control already applied to the C2 admin panel in this lab.

Track

Treat the bundled runtime as a standing exposure with a vendor dependency: re-scan on each release, escalate to the vendor, and hold the compensating control until the pin is lifted.

Status

At assessment time, access restriction remained pending. Closure requires an external denial check and a successful authorized-path dashboard test.

Takeaway

A CVSS score is a starting point, not a verdict. The scanner's 9.8 result was real, the vulnerable component was real, and its process faced the internet — and it still wasn't the emergency the number implied, because validation against the running config eliminated the RCE reading entirely and narrowed twenty CVEs to a single plausibly-reachable availability issue. That gap, in both directions, is the whole job: a scanner reports what it has a plugin for; an analyst determines what's true here. The finding that mattered most in this environment was pinned by a vendor, invisible to one of two scanners, and only understandable after the number stopped being the answer and started being the question.
