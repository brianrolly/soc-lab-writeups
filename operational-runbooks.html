Overview

A detection that fires is only useful if someone knows what to do next. These are the two runbooks reached for most often — one to respond to a high-severity Linux alert, one to triage scan activity across two different event schemas.

Runbook I

Linux IR for a high-severity alert

A fixed sequence so a level-10+ alert is worked the same way every time — and so volatile evidence is captured before containment destroys it. Fifteen steps in the full runbook; this is the spine.

workflowthe spine
confirm → processes → network → capture → contain
        → forensics → hunt persistence → remediate → report
01

Confirm — pull the alert with full audit context

manager
wazuh manager
jq -r 'select((.rule.level//0)>=10)
  | [.timestamp,.agent.name,.rule.id,.rule.description,
     (.rule.mitre.id//[]|join(",")),.data.audit.command,
     .data.audit.exe,.data.audit.pid,.data.audit.ppid]
  | @tsv' /var/ossec/logs/alerts/alerts.json
02

Processes — walk the tree from the flagged PID

victim host
ps -eo pid,ppid,user,lstart,cmd --sort=start_time | tail -100
pstree -asp $PID; readlink -f /proc/$PID/exe; ls -la /proc/$PID/fd
# flag: binaries in /tmp /dev/shm /root; curl/python/nc; odd parent/child
03

Network — find the outbound session

C2 hunt
victim hostoutbound connections
ss -tunap | grep -vE '127.0.0.1|::1'    # every non-loopback socket
lsof -Pan -i -n -p $PID                  # the flagged process's connections
# flag: established outbound to an unknown IP from a /tmp or agent process
04

Evidence first — capture before touching anything

victim hostpreserve the C2 traffic
mkdir -p /root/ir-evidence
tcpdump -i any -nn -s0 host $REMOTE_IP \
  -w /root/ir-evidence/suspect-$REMOTE_IP-$(date -u +%Y%m%d-%H%M%S).pcap
disciplinePacket capture and process/file state are preserved before any kill or block — containment destroys volatile evidence.
05

Contain — block the C2, keep SSH and telemetry alive

UFW
victim host
ufw allow from $ADMIN_IP to any port 22 proto tcp   # don't lock yourself out
ufw allow out to 198.51.100.10 port 1514 proto tcp  # keep Wazuh reporting
ufw deny out to $REMOTE_IP                           # cut the beacon
ss -ntp state established | grep $REMOTE_IP || echo "connection dropped"
noteOrder matters — allow SSH and Wazuh before the block, so containment severs neither your access nor your visibility.
06

Forensics — capture memory, collect, hash, timeline

most volatile first
victim hostRAM — capture before anything else
# full memory image — avml is a single static binary, no kernel module needed
./avml /root/ir-evidence/mem-$(hostname)-$(date -u +%Y%m%d-%H%M%S).lime
# analyse offline with Volatility 3 (Linux):
#   vol -f mem-*.lime linux.pslist   linux.pstree
#   vol -f mem-*.lime linux.netstat  linux.bash   linux.malfind
victim hostlive artifacts from /proc
# the live binary straight out of /proc — recovers it even if unlinked on disk
cp /proc/$PID/exe   /root/ir-evidence/suspect.bin
cat /proc/$PID/maps /proc/$PID/environ /proc/$PID/status > /root/ir-evidence/proc-$PID.txt
last -Fw > …/logins.txt ; lastb -Fw > …/failed.txt ; cp ~/.bash_history …/
journalctl --since "-4 hours" > /root/ir-evidence/journal.txt
victim hostintegrity + timeline
# hash every artifact — this is what makes it evidence, not just a copy
sha256sum /root/ir-evidence/* | tee /root/ir-evidence/SHA256SUMS
# filesystem super-timeline (recovers deleted entries) with The Sleuth Kit
fls -r -m / /dev/sda2 > /root/ir-evidence/bodyfile
mactime -b /root/ir-evidence/bodyfile -d > /root/ir-evidence/timeline.csv
tooling & custodyAcquire with avml / LiME; analyse memory in Volatility 3; disk and timeline via Sleuth Kit / Autopsy / plaso; broad live triage with Velociraptor or UAC. Every item is logged with collector, UTC time, source path and SHA-256 — captured before the kill, hashed at collection.
07

Hunt persistence — before declaring it over

victim host
systemctl list-unit-files | grep -Ei 'agent|cron|sandcat|splunk'
grep -RniE 'curl|wget|/tmp|/dev/shm|nc |socat|sandcat' \
  /etc/systemd/system /etc/cron* /var/spool/cron /root /home 2>/dev/null
find /root /home -name authorized_keys -exec cat {} \;   # planted keys
08

Remediate — stop it, and stop it respawning

victim host
kill $PID; ps -p $PID || echo "stopped"
systemctl disable --now $SERVICE; systemctl daemon-reload   # if it respawns
09

Report — export a portable evidence bundle

manager
wazuh manager
CASE="ir-$(date -u +%Y%m%d-%H%M%S)"; mkdir -p /root/$CASE
jq -c 'select(.agent.name==$victim)' …/alerts.json   > /root/$CASE/alerts.json
jq -c 'select(.agent.name==$victim)' …/archives.json > /root/$CASE/archives.json
jq -r '…|@tsv' /root/$CASE/alerts.json > /root/$CASE/alert-summary.tsv
outputA timestamped case folder — raw alerts, raw archives, and a readable command timeline — plus the filled analyst-notes template that closes the runbook.

Runbook II

Scan triage — reading two schemas

OPNsense firewall events and Suricata EVE events describe the same packet with different field names. An analyst who doesn’t know the mapping reads blank columns as missing data. The runbook makes it a lookup.

Meaning Firewall (pf) Suricata EVE
Source IPdata.srcipdata.src_ip
Source portdata.srcportdata.src_port
Dest IPdata.dstipdata.dest_ip
Dest portdata.dstportdata.dest_port
Protocoldata.protocoldata.proto
Enforcementdata.action=blockdata.alert.action
Detectionrule.descriptiondata.alert.signature
resultBlank Suricata columns on a firewall event are expected, not a gap — and the analyst gets a ready set of hunting columns for each event type.

Takeaway

Good runbooks remove improvisation from the moments that can least afford it. They encode the sequence, anticipate where an analyst gets stuck, and ensure evidence is captured before containment destroys it — the difference between reacting to an alert and working it.
