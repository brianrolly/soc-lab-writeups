From Alert to Action

Detections are half the job. These are the runbooks that turn a firing alert into a decision — a high-severity Linux IR flow, and a scan-triage guide for reading two event schemas at once.

Overview

A detection that fires is only useful if someone knows what to do next. These are the two runbooks reached for most often — one to respond to a high-severity Linux alert, one to triage scan activity across two different event schemas.

Runbook I

Linux IR for a high-severity alert

A fixed sequence so a level-10+ alert is worked the same way every time. Capture a bounded network sample and process state before containment when it is safe to do so; if active harm demands immediate isolation, contain first and document the evidence lost. Fifteen steps in the full runbook; this is the spine.

workflowthe spine
confirm → processes → network → capture → contain
        → forensics → hunt persistence → remediate → report

Before running the example commands, set PID, REMOTE_IP, ADMIN_IP and WAZUH_MANAGER_IP from verified case evidence. Set SERVICE only if the process belongs to a confirmed malicious unit; set DISK_IMAGE only when a verified forensic image is available. Adapt paths and ports to the in-scope host.

01

Confirm — pull the alert with full audit context

manager
wazuh manager
jq -r 'select((.rule.level//0)>=10)
  | [.timestamp,.agent.name,.rule.id,.rule.description,
     (.rule.mitre.id//[]|join(",")),.data.audit.command,
     .data.audit.exe,.data.audit.pid,.data.audit.ppid]
  | @tsv' /var/ossec/logs/alerts/alerts.json
02

Processes — walk the tree from the flagged PID

victim host
ps -eo pid,ppid,user,lstart,cmd --sort=start_time | tail -100
pstree -asp $PID; readlink -f /proc/$PID/exe; ls -la /proc/$PID/fd
# flag: binaries in /tmp /dev/shm /root; curl/python/nc; odd parent/child
03

Network — find the outbound session

C2 hunt
victim hostoutbound connections
ss -tunap | grep -vE '127.0.0.1|::1'    # every non-loopback socket
lsof -Pan -i -n -p $PID                  # the flagged process's connections
# flag: established outbound to an unknown IP from a /tmp or agent process
04

Preserve volatile evidence if containment can wait

victim hostpreserve the C2 traffic
umask 077; mkdir -p /root/ir-evidence
timeout --preserve-status --signal=INT 15s tcpdump -i any -nn -s0 "host $REMOTE_IP" \
  -w "/root/ir-evidence/suspect-$(date -u +%Y%m%d-%H%M%S).pcap"
victim hostprocess state before stopping it
cp "/proc/$PID/exe" /root/ir-evidence/suspect.bin
cp "/proc/$PID/maps" "/root/ir-evidence/proc-$PID.maps"
cp "/proc/$PID/environ" "/root/ir-evidence/proc-$PID.environ"
cp "/proc/$PID/status" "/root/ir-evidence/proc-$PID.status"
# If containment can wait, acquire memory while the process is still running:
./avml "/root/ir-evidence/mem-$(date -u +%Y%m%d-%H%M%S).lime"
disciplineThe packet capture is capped at 15 seconds; process state and, when feasible, RAM are acquired before termination. Restrict access to the evidence folder: process environment data may contain secrets.
05

Contain — stop the active C2 and block reconnection

UFW
victim host
ufw allow from "$ADMIN_IP" to any port 22 proto tcp
ufw allow out to "$WAZUH_MANAGER_IP" port 1514 proto tcp
ufw deny out to "$REMOTE_IP"   # prevent a new connection
kill -TERM "$PID"                # close the established session
ss -ntp state established | grep -F -- "$REMOTE_IP" || echo "No established C2 socket observed"
verifyStock UFW accepts established traffic before user deny rules, so the deny rule alone may leave an active beacon connected. Confirm the suspect process has stopped, watch for respawn, and check host or perimeter flow logs for continued traffic. If it survives or resumes, isolate the host through the approved response path.
06

Forensics — collect, timeline, then hash

post-containment
analyst workstationmemory acquired in step 04, if safe
# analyse offline with Volatility 3 (Linux):
#   vol -f mem-*.lime linux.pslist   linux.pstree
#   vol -f mem-*.lime linux.netstat  linux.bash   linux.malfind
victim hosthost logs
last -Fw > /root/ir-evidence/logins.txt
lastb -Fw > /root/ir-evidence/failed.txt
cp /root/.bash_history /root/ir-evidence/bash_history.txt
journalctl --since "-4 hours" > /root/ir-evidence/journal.txt
case evidence copyintegrity + timeline
# Optional offline timeline from a verified forensic disk image:
if [ -n "${DISK_IMAGE:-}" ]; then
  fls -r -m / "$DISK_IMAGE" > /root/ir-evidence/bodyfile
  mactime -b /root/ir-evidence/bodyfile -d > /root/ir-evidence/timeline.csv
fi
# After collection finishes, hash every completed file (except this manifest):
find /root/ir-evidence -maxdepth 1 -type f ! -name SHA256SUMS -print0 \
  | sort -z | xargs -0 -r sha256sum > /root/ir-evidence/SHA256SUMS
tooling & custodyAcquire RAM with avml when safe; analyse it offline with Volatility 3. Run fls against a verified disk image on the analyst's evidence copy, not a guessed live partition. Record collector, UTC time and source path, then hash completed artifacts. If immediate containment delayed memory acquisition, a later image may miss the live process.
07

Hunt persistence — before declaring it over

victim host
systemctl list-unit-files | grep -Ei 'agent|cron|sandcat|splunk'
grep -RniE 'curl|wget|/tmp|/dev/shm|nc |socat|sandcat' \
  /etc/systemd/system /etc/cron* /var/spool/cron /root /home 2>/dev/null
find /root /home -name authorized_keys -exec cat {} \;   # planted keys
08

Remediate — verify the stop and remove persistence

victim host
ps -p "$PID" || echo "process stopped"
systemctl disable --now "$SERVICE"   # only after confirming the malicious unit
09

Report — export a portable evidence bundle

manager
wazuh manager
VICTIM_AGENT="<confirmed-agent-name>"
CASE="ir-$(date -u +%Y%m%d-%H%M%S)"; mkdir -p "/root/$CASE"
jq -c --arg victim "$VICTIM_AGENT" 'select(.agent.name == $victim)' \
  /var/ossec/logs/alerts/alerts.json > "/root/$CASE/alerts.json"
# Archives are available only if archive logging was enabled:
if [ -f /var/ossec/logs/archives/archives.json ]; then
  jq -c --arg victim "$VICTIM_AGENT" 'select(.agent.name == $victim)' \
    /var/ossec/logs/archives/archives.json > "/root/$CASE/archives.json"
fi
jq -r '[.timestamp, .agent.name, .rule.id, .rule.description,
        (.data.audit.command // "")] | @tsv' "/root/$CASE/alerts.json" \
  > "/root/$CASE/alert-summary.tsv"
outputA timestamped case folder — raw alerts, archives if enabled, and a readable alert summary — plus the filled analyst-notes template that closes the runbook.

Runbook II

Scan triage — reading two schemas

OPNsense firewall events and Suricata EVE events describe the same packet with different field names. An analyst who doesn’t know the mapping reads blank columns as missing data. The runbook makes it a lookup.

Meaning Firewall (pf) Suricata EVE
Source IPdata.srcipdata.src_ip
Source portdata.srcportdata.src_port
Dest IPdata.dstipdata.dest_ip
Dest portdata.dstportdata.dest_port
Protocoldata.protocoldata.proto
Enforcementdata.action=blockdata.alert.action
Detectionrule.descriptiondata.alert.signature
resultBlank Suricata columns on a firewall event are expected, not a gap — and the analyst gets a ready set of hunting columns for each event type.

Takeaway

Good runbooks remove improvisation from the moments that can least afford it. They encode the sequence, anticipate where an analyst gets stuck, and ensure evidence is captured before containment destroys it — the difference between reacting to an alert and working it.
